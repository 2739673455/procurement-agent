# 采购业务平台详细设计

版本：设计草案 v5；日期：2026-09-09；状态：设计中，平台尚未实现。

本文统一维护业务对象、业务规则和技术设计。完整角色步骤见[平台 README](../README.md)，逐表字段和约束见[数据库设计](DATABASE.md)。数据库 v3 已补齐本轮流程实体的字段设计；API、迁移与运行验证尚未实现。

## 1. 定位、范围与默认口径

`platform/` 是独立部署的采购业务后端，使用 Python + FastAPI，内部采用模块化单体。采购、供应商、财务、库存四个模块共用一个业务数据库，通过模块服务和流程协调协作。`assistant/` 独立部署、使用独立数据库，只通过业务 API 访问平台。`web/` 提供业务操作页面和助手入口。

平台必须在助手停止运行时，仍支持人工完成供应商准入、申请审批、询价比价、订单、收货、发票核对和付款登记。

以下为目标范围与实施边界；多公司、多币种和非实物采购已确定，具体公司制度仍需配置：

| 项目 | 目标范围 | 实施边界 |
| ---- | -------- | -------- |
| 组织 | 多公司、多部门；公司限定数据权限、准入、预算及结算 | 不跨公司合并采购单据 |
| 币种 | 交易币种、预算币种、本位币及汇率快照 | 首批普通付款同应付币种；跨币种结算另补差额规则 |
| 采购对象 | 实物、服务、软件许可与订阅；按数量或金额验收 | 非实物不强制物料编码和仓库 |
| 寻源 | 协议下单、RFQ、RFP、招标及有审批依据的例外 | 首期供应商线下交互；各方式按业务切片交付 |
| 合同与订单 | 全部通过采购订单履约；合同按固定范围派生订单或按框架分次下单；审批、签署、下达和变更分别留痕 | 合同在采购模块，不建设独立合同服务 |
| 审批 | 按公司、类别、金额和动作配置固定顺序节点 | 会签、加签和可视化设计器后续扩展 |
| 预算 | 明细支持预算分配；申请审批通过建立预占，订单批准（含合同签前审批派生核准）转承诺占用（多退少补） | 同一采购义务不得在合同和订单重复占用 |
| 发票与付款 | 履约匹配、应付、付款申请、授权、实付登记与复核 | 不建设银行支付、税务查验和完整会计核算 |
| 仓储 | 实物收退货、领用、盘点及库存流水 | 不允许负库存；非实物验收归采购模块 |

最低询价家数、审批金额阈值、交付提醒提前天数、发票舍入容差均为配置项，不在代码中写死。规则缺失时阻止相关提交并提示配置问题。付款登记不代表平台发起了银行付款，发票核对不代表税务真伪验证。

### 1.1 参考来源与采用方式

参考入口为用户指定的 [IBM TRIRIGA 11.6 项目采购管理](https://www.ibm.com/docs/zh/tririga/11.6.0?topic=projects-managing-project-procurement)。该入口直接读取受限，当前通过 IBM 官方可检索的同版本子章节及手册核对内容；不是逐页复刻整个 TRIRIGA 产品。

| 参考章节 | 可核对的 IBM 行为 | 本平台设计决定 |
| -------- | ---------------- | -------------- |
| [采购管理流程](https://www.ibm.com/docs/zh/tririga/11.6.0?topic=mpp-procurement-management-process) | 分配的采购人员选择采购方式；已有协议可下单，也可发起询价或招标 | 增加采购任务分配和方式选择，不强制所有采购经过询价 |
| [创建 RFQ](https://www.ibm.com/docs/en/tririga/11.6.0?topic=quote-creating-requests-quotes) | 记录产品或服务、成本及候选供应商，并按配置送审 | 询价文件与供应商报价分开，发布前冻结范围和审批依据 |
| [创建 RFP](https://www.ibm.com/docs/en/tririga/11.6.0?topic=proposal-creating-requests-proposals) | RFP 可导入标准合同资料，再进入审批 | 支持引用合同资料；本项目不要求所有方案征集先有合同，属于本地化调整 |
| [向供应商发送征集文件](https://www.ibm.com/docs/en/tririga/11.6.0?topic=process-sending-bids-requests-vendors) | 已发布文件发送后，由供应商响应 | 发布、送达、响应分别留记录；首期内部代录线下往来 |
| [RFQ/RFP 授予订单](https://www.ibm.com/docs/en/tririga/11.6.0?topic=process-awarding-purchase-orders) | 分析响应后可以授予采购订单 | 获批选择结果生成采购文件草稿，继续执行本公司的订单审批 |
| [采购管理手册：招标流程](https://www.ibm.com/docs/en/SSFCZ3_11.6/pdf/pdf_tri_procure_mng.pdf) | 创建招标、收集响应、分析和授予后形成标准合同；过程中可以澄清 | 增加招标分支、评审记录与澄清记录；招标和 RFQ 不混用业务名称 |
| [项目管理手册：合同及合同变更](https://www.ibm.com/docs/en/SSFCZ3_11.6/pdf/pdf_tri_pgm_proj_mng.pdf) | 合同可来自招标或单独建立；标准合同的变化通过变更单记录 | 生效合同保持历史版本，以审批后的变更单调整后续义务 |
| [创建采购订单](https://www.ibm.com/docs/en/tririga/11.6.0?topic=purchases-creating-purchase-orders) | 订单可从征集结果生成，也可手工创建；可包含产品和服务 | 每种订单都须有合法采购依据；服务订单不要求关联仓库 |
| [发票](https://www.ibm.com/docs/en/tririga/11.6?topic=vendors-invoices) | 区分合同、任务、公用事业和采购订单等发票依据 | 统一发票对象，仅关联订单，合同由订单追溯；暂不建设公用事业计量与任务计费 |
| [合同经理与采购经理角色](https://www.ibm.com/docs/en/tririga/11.6.0?topic=portals-contract-manager-purchasing-manager-roles) | 管理采购、合同及合同交付表现，岗位可组合 | 保留采购负责人、采购员和合同责任；按动作权限实施职责分离 |

以上是来源事实与本项目决定的对照。本文的角色分工、状态名、预算时点、付款额度算法、数据实体和上线顺序是本平台方案，不是 IBM 的字段定义或企业通用制度。IBM 采购概述提到付款申请及支付放行，但当前未取得其完整专章；本平台付款申请和授权按下文独立定义。

不因采用 TRIRIGA 参考而新增项目进度、施工分包、租赁会计、设备维护、空间管理或公用事业计量模块。项目可作为采购费用归属维度；法定招投标程序须另按适用制度配置，本文的招标分支不等于已实现电子招投标合规平台。

## 2. 用户、工作台与页面

### 2.1 角色与责任

| 角色          | 主要操作                                             | 主要数据范围                       |
| ------------- | ---------------------------------------------------- | ---------------------------------- |
| 申请人        | 新建需求、提交申请、补充资料、查看进度               | 本人单据及获授权的部门数据         |
| 采购员        | 供应商查询、询价发布、密封响应盲收登记、参与开标、定标建议、订单与催交待办 | 分配的组织和采购单据               |
| 监标人/开标见证人 | 截标后开标授权与监督、见证集中解密与开标记录生成     | 负责的招标或询价征集单据           |
| 采购负责人    | 申请、定标、订单审批；异常决策                       | 获授权组织                         |
| 供应商管理员  | 档案、资质资料、准入申请与状态维护                   | 获授权供应商范围                   |
| 仓管员        | 收货、退货、领用、盘点调整                           | 获授权仓库                         |
| 质检员 | 检验到货、提交检验结果与证据、发起退货 | 获授权公司及检验任务 |
| 业务验收人 | 核验非实物交付、提交验收单及证据 | 获授权采购履约范围 |
| 验收审批人 | 审批分配的非实物验收单 | 对应审批待办；最终审批人与提交人分离 |
| 退货申请人 | 提交实物退货申请及证据 | 获授权的原收货记录；不自动取得库存写权限 |
| 财务人员      | 预算维护申请、发票核对、付款登记                     | 获授权法人、部门与预算项           |
| 审批人/复核人 | 完成分配给自己的审批或复核                           | 对应待办关联单据的必要字段         |
| 异常负责人 | 处理并申请关闭被指派的异常；按类别由采购、质检、业务或财务人员担任 | 指派范围与业务权限的交集；不绕过财务/质量审批 |
| 评价参与人 | 按仓管、质检、业务、财务、采购角色提交本维度评分 | 对应公司、订单及评价维度；不可代改其他角色评分 |
| 系统管理员    | 账号、权限、规则、基础配置                           | 配置管理；不自动获得所有业务审批权 |
| 助手服务      | 授权查询、草稿创建、提交审批、获准的业务动作         | 用户委托权限与工具权限的交集       |

同一人可以有多个角色，但本人提交的申请、定标、订单、预算调整、库存调整、退货、需审批的非实物验收和付款登记不能由本人完成最终审批；开标解密必须由监标人见证，采购员不可单人私下拆封。试点数据中至少准备两名可相互复核的人员；没有合格审批人时停留待处理，不能自动通过。

## 3. 模块边界与工程结构

### 3.1 模块职责

| 模块           | 拥有的数据和规则                                   | 对外服务示例                         |
| -------------- | -------------------------------------------------- | ------------------------------------ |
| `foundation`   | 用户、组织、角色、物料、单位、仓库定义、附件、审计 | 授权校验、主数据查询、单据登记       |
| `suppliers`    | 档案、供货品类、资质、准入与运营状态、绩效快照     | 检查可采购状态、候选查询             |
| `procurement`  | 申请、任务、征集响应、授予、合同订单、变更及非实物验收         | 创建订单草稿、检查可收货数量         |
| `finance`      | 预算与分配、发票应付、付款申请授权及实付登记       | 占用/释放预算、核对发票、登记付款    |
| `inventory`    | 收退货单、出入库单、库存余额与流水                 | 收货过账、退货过账、库存查询         |
| `approvals`    | 审批规则版本、审批实例、节点和决策记录             | 创建审批、校验当前审批人、记录决策   |
| `workflows`    | 跨模块动作与事务协调，不复制模块账本               | 完成订单审批、收货过账、取消订单余量 |
| `integrations` | 助手授权接入、幂等记录、变化记录和发布游标         | 查询操作结果、拉取业务变化           |

模块内部可使用所属 ORM 模型；跨模块通过公开服务交换明确的输入输出结构。跨模块只读报表可使用显式查询服务关联表，禁止通过报表路径修改其他模块数据。前端和助手共用同一业务动作。

### 3.2 规划目录

```text
platform/
  pyproject.toml
  src/
    procurement_platform/
      main.py
      core/                 # 配置、数据库会话、日志、错误处理
      foundation/

  migrations/
  tests/
    unit/
    integration/
    contract/
    acceptance/
  docs/

    DATABASE.md             # 逐表字段、约束与索引
```

`platform/` 仅作项目目录，Python 包名使用 `procurement_platform`，避免与标准库 `platform` 重名。每个业务模块先使用 `router.py`、`schemas.py`、`models.py`、`service.py` 和必要的 `queries.py`；复杂后按业务对象拆分，不先搭建通用 CRUD 框架。

路由处理协议、身份和输入输出，服务处理业务规则，顶层用例管理事务，查询函数处理列表与报表。FastAPI 使用 `APIRouter` 组织模块并统一注册依赖。[FastAPI 多模块组织文档](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

### 3.3 数据访问与运行方式

使用 SQLAlchemy + PostgreSQL，Alembic 管理迁移。首期选择同步数据库访问和同步业务路由，保持事务代码直接可读；每个请求或后台任务独立创建 Session，同一次跨模块用例传递同一个 Session，内部服务不得自行提交。SQLAlchemy Session 不跨并发线程或任务共享。[SQLAlchemy Session 文档](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)

助手模型调用不进入平台进程。平台关键业务写入在请求事务内完成；事件发布、报表和导入使用可恢复的后台作业。FastAPI `BackgroundTasks` 不承担必须跨进程重启恢复的记账工作；复杂后台任务可接 Celery，但数据库仍是任务与业务结果的权威记录。[FastAPI 后台任务说明](https://fastapi.tiangolo.com/tutorial/background-tasks/)

## 4. 业务对象与模块归属

以下为领域对象，不表示每一项都与一张物理表一一对应。主表记录共同信息，明细记录采购范围，关系记录来源分配；实际表和约束需在数据库重构时逐项展开。

| 模块 | 业务对象 | 主要内容和关联 |
| ---- | -------- | -------------- |
| 采购 | 采购申请 | 公司、申请人、费用归属；明细包含采购类型、类别、描述、数量或金额、币种、验收方式 |
| 采购 | 采购任务 | 关联申请明细、责任采购员、分配人与分配历史；不同明细可委派不同人员 |
| 采购 | 采购方式决定 | 采购包、方式、规则版本、适用协议、选择原因、例外审批依据 |
| 采购 | 征集文件 | RFQ/RFP/招标类型、范围明细、邀请名单、截止时间、评价规则、发布版本 |
| 采购 | 供应商响应 | 对应征集及其版本、供应商、递交密封凭据、递交时间、开标解密记录、报价明细或方案、有效期 |
| 采购 | 澄清记录 | 提问、回复、发送范围及时间；改变征集范围时关联补遗或新一轮征集 |
| 采购 | 评审记录 | 评审人、标准版本、逐项结论、理由及证据；技术评审和商务评审可分工 |
| 采购 | 授予记录 | 获批供应商、响应版本、范围分配、数量或金额、拟生成文件类型 |
| 采购 | 采购合同 | 标准合同、框架采购协议、服务协议；分别保存类型、签署、生效条件和订单生成方式 |
| 采购 | 合同明细及履约计划 | 约定范围、价格、额度、期间、里程碑、验收及付款条件 |
| 采购 | 采购订单 | 引用授予或协议依据；明细记录履约标的、预算分配和来源范围 |
| 采购 | 采购变更单 | 唯一目标合同或订单、目标基准版本、变更前后值、原因、金额差额及审批 |
| 采购 | 交付通知 | 供应商预计交付信息、来源订单明细及附件；不更新库存或预算 |
| 采购 | 非实物验收单 | 关联订单明细；成果、里程碑、许可或服务期间及通过数量或金额 |
| 库存 | 物料档案与库存余额 | 只记录实物物料，管理仓库、库位、现存量与批次；不记录服务及虚拟资产 |
| 库存 | 收货及退货单 | 实物履约和库存凭证，关联采购承诺明细；保留实收、退回及冲销关系 |
| 供应商 | 档案、公司准入和绩效 | 区分潜在供应商（PROSPECT，参与竞争寻源）与正式准入合格供应商（APPROVED，签约下单）；准入状态不能由报价记录代替 |
| 财务 | 预算账户及分配 | 公司、预算币种、期间、部门及可选项目维度；采购明细可以拆分承担额度 |
| 财务 | 预算预占、承诺与执行流水 | 对采购申请建立预占，对订单明细（含合同派生订单）正式占用，执行、释放或冲销，关联当时汇率快照 |
| 财务 | 发票及应付分配 | 原始票据、订单明细、收货或验收依据、匹配结果、复核状态 |
| 采购 | 支付计划 | 承诺明细、计划版本、预付/验收后支付类型、金额或比例、触发条件与到期日；随合同或订单审批 |
| 财务 | 付款申请 | 普通应付或预付计划来源、本次金额、计划日期、收款信息；提交后占用对应额度 |
| 财务 | 预付余额及核销 | 已确认预付实付、对应采购范围、未核销余额；核销关联已确认发票及复核记录 |
| 财务 | 支付执行记录 | 线下出款前认领授权额度，记录执行人、执行结果及待核实状态；防止重复出款 |
| 财务 | 付款授权 | 付款申请获批版本的不可变授权结果及有效余额；不是已付款记录 |
| 财务 | 付款登记 | 实际支付凭证、授权分配、发票分配及复核结果；支持一次授权分次支付 |
| 公共能力 | 审批、附件、审计、异常与幂等 | 绑定业务对象和内容版本；不能绕过领域动作直接更新状态 |

采购承诺是获准履行和支付的采购义务，统一由采购订单明细 `purchase_order_line.id` 承载。合同管理条款和签署，订单引用合同明细及版本；无合同采购的订单可不引用合同。收货、验收、支付计划、预算分配和发票均引用订单明细；付款申请及实付通过计划或应付分配追溯订单，不增加合同来源分支。

### 4.1 通用约定

- 主键使用 UUID，业务编号由数据库序列生成，允许跳号；唯一键为法人、单据类型、编号，不按时间戳或当前最大值加一生成编号。
- 业务单据统一关联 `business_document`：`id/document_type/number/legal_entity_id/department_id/owner_id/revision/lock_version/status/created_at/updated_at`；领域表以该 ID 作为主键和外键。通用审批和附件通过它建立真实关联。
- `revision` 是内容版本；另设 `lock_version` 控制并发更新。审批快照绑定内容版本，库存变化等独立事件不隐式改写获批的采购价格。
- 明细具有稳定 ID、行号和来源明细 ID。供应商名称、物料规格、单位和成交价格保留单据快照，主数据改名不覆盖历史单据。
- 业务金额使用 Decimal；数据库金额规划为 `numeric(24,6)`，按币种小数位校验；单价 `numeric(20,6)`、数量 `numeric(20,6)`、税率 `numeric(9,6)`。JSON 中金额、单价和数量以十进制字符串传输。
- 行金额按数量乘未税单价依交易币种小数位舍入，税额按行舍入，含税额为二者之和；单据金额为各行金额合计。舍入统一为 ROUND_HALF_UP，余量结算最后一笔吸收合法尾差。
- 时间存储为 UTC 带时区时间；交期、预算期间等业务日期按企业时区 Asia/Shanghai 解释。税率由人工录入和规则校验，不由模型推测。
- 正式单据、审批和已过账流水不物理删除；主数据停用，草稿作废。错误账目通过关联原记录的反向流水修正，保留历史。
- 关键关联同时校验法人一致性；可用复合外键约束的关系在数据库约束，禁止通过 UUID 猜测绕过组织边界。

### 4.2 数据库设计边界

逐表字段、类型、默认值、主外键、约束及索引仅在[数据库详细设计](DATABASE.md)维护，本文不重复单表目录。字段字典仍为待重构草案，新增业务关系及约束需落实后才能实施。

### 4.3 业务关联规则

供应商准入状态包含 `PROSPECT`（潜在）、`DRAFT`、`IN_REVIEW`、`APPROVED`、`REJECTED`，运营状态为 `ACTIVE/SUSPENDED/ARCHIVED`。潜在供应商（`PROSPECT`）可被邀请或参与 RFQ/RFP/招标的密封竞价与方案响应；但在定标后，订单核准（含合同派生订单）前必须完成正式准入审批转为 `APPROVED` 且 `ACTIVE`。停用限制新采购，不阻止历史收货、对账和付款登记。

寻源响应在截止前严格实施密封管理（状态为 `SEALED`），各家递交时仅记录密封凭证哈希与时间，接口严禁返回报价明细；截止后由开标事务（`UNSEALED`）集中解密生成开标记录表，方可进入比价与评审。

申请可下单范围 = 当前批准需求范围 − 同一稳定需求项跨版本有效订单分配。通过 purchase_request_item 锁定来源，order_source_allocation 保存准确版本及已消费/释放范围；数量型按单位，金额型服务按批准范围金额，成交降价不能扩张采购范围。退货恢复范围不自动恢复预算预占，重新采购前须审批恢复相应预占。

库存不负责财务账本，财务不直接修改库存；`correction_request` 归属 `workflows`，由它协调各模块的反向记账服务。

### 4.4 跨模块关联与一致性边界

库存与财务保持独立的数据归属和业务服务。以下场景通过 `workflows` 协调：

- **收货与预算**：当前采用“收货时占用转已执行”的预算口径，因此收货过账、库存增加和预算更新必须在一个数据库事务内完成。这是本方案选择的强一致性边界；如果企业改用其他预算执行口径，需要同步调整流程。
- **发票匹配**：财务模块读取订单和净收货量，管理自己的发票分配记录；匹配本身不增加或扣减库存。
- **退货与冲销**：执行前核查发票分配等下游约束，获准后由各模块更新自己的流水；当前设计不允许绕过财务关联直接退掉已分配收货数量。
- **独立业务**：日常领用和盘点不触发采购预算更新；预算额度调整和付款登记也不改变库存。

共用事务不意味着合并模块或相互直接写表。首期由流程协调层调用两个模块的服务并统一提交事务。

## 5. 采购方式、合同与审批

人工步骤统一见[平台采购流程](../README.md#逐步执行流程)，本节维护分支和生效规则。

### 5.1 流程分支及责任边界

基础数据维护是前置条件。单次采购从申请开始，经业务审批立项后，由系统或采购负责人分配采购任务并核实需求，再选择采购方式；采购负责人可在不改变申请内容的情况下改派采购员，保留交接记录。

| 方式 | 适用判断 | 寻源输入与供应商输出 | 后续路径 |
| ---- | -------- | -------------------- | -------- |
| 协议下单 | 本公司已有生效且覆盖本次范围的框架采购协议或服务协议 | 核对约定品目、价格、有效期和可用额度；必须为已准入合格供应商 | 申请明细关联协议明细，准备订单 |
| RFQ 询价 | 需求规格和价格比较口径已明确 | 询价单 → 密封报价凭证 → 集中开标解密 | 比价、授予审批，按公司规则与完整条件自动核准或转人工审批 |
| RFP 方案征集 | 需比较解决方案、交付方法或服务能力 | 方案征集文件 → 密封方案及报价凭证 → 集中开标解密 | 综合评审、授予审批、订单或合同草稿 |
| 招标 | 公司采购制度要求采用招标方式 | 招标文件 → 密封投标响应凭证 → 集中开标解密 | 评标、授予审批、合同草稿 |
| 例外采购 | 单一来源、紧急采购或响应数量不足等有充分依据 | 例外申请、理由和支撑材料 | 经授权审批后按指定路径执行，仍需订单及预算校验，必要时另有合同 |

询价、报价、评审是不同阶段，分别对应征集文件、供应商响应和授予记录。RFQ 的结果称比价和供应商选择；招标的结果称评标及定标。多个方式可以复用版本、附件、邀请与审批基础能力，但不能把供应商报价直接写进询价单覆盖原始要求。

需求明细可以拆为多个采购包；本期一次征集先限定一个申请，跨申请合并寻源待补齐来源分配模型后开放，同公司多条明细可合并评审。分包、合并和分配均保留来源明细及数量或金额；不得跨公司合并成一张对外采购文件。申请人填写公司和需求信息，财务负责无法自动匹配的预算归属；采购员不能以库存数量自行改写需求。

### 5.2 合同约束与统一订单执行

本平台只有采购订单一种履约与结算执行对象，物理表沿用 `purchase_order`、`purchase_order_line`，不另建“执行单”兼容层。采购订单支持实物、服务、许可和订阅；非实物订单记录范围、金额、期间和里程碑，不强制填写仓库或物流字段。

- **无合同采购**：从获批 RFQ/RFP 授予生成订单，无偏离且满足公司规则、准入与预算校验时自动核准；有偏离、公司要求人工审批或其他自动核准条件不满足时进入明确待办。
- **框架协议分次下单**：合同约定范围、价格和额度；按每次实际需求创建订单，分别审批并占用预算及协议可用额度。
- **一次性或固定范围合同**：合同送审时生成可审阅的订单及明细草稿，随合同一起冻结范围、计划和预算分配。合同最终核准时同事务核准对应订单、结转预算预占并占用协议范围；预算来源始终是订单明细，不另写合同预算占用。没有偏离的派生订单复用合同审批决定，不重复人工审批。

一次性合同的订单在签前核准后处于 `APPROVED`，但执行资格为 `WAITING_CONTRACT`；合同双方签署、生效条件满足后才开放下达、收货、验收及付款申请。内部核准和对外执行必须分开，不能仅检查 APPROVED 就提前付款。签署激活不再次扣预算。合同与派生订单均存在真实、可审阅记录，不是仅为外键补一个空壳订单。

合同签署文件可以作为其派生订单的对外送达依据，采购员登记关联凭证即可下达订单，无需重复签署另一份采购文件；普通订单仍按约定送达。若合同未签成，经批准终止合同及所有未执行派生订单，同事务释放未履约占用。合同签署和终止并发时锁定同一合同及派生订单，不能一边释放预算一边允许履约。

一个合同可对应多张订单，但一张订单最多引用一个合同，合同可选；公司、供应商和交易币种须一致，不满足则拆单。订单明细引用确定的合同明细及版本，分次下单或分批交付不得重复消耗同一额度。框架协议的保底采购承诺也必须落实为订单范围并提前占用预算，不能以“只是框架”规避承诺控制；未支持保底规则时阻止核准。

合同变更不直接改写已核准订单。一次性合同涉及已有订单的范围或价格变化时，提交关联变更包，列明受影响订单和差额，统一审批后在一个事务中应用，预算只按订单差额调整；需双方确认时完成确认后才生效。框架条款新版本默认仅供新订单使用。已履约、开票或支付事实保持历史版本，不能通过合同改小金额抹去。

### 5.3 寻源合规、密封开标与准入控制

1. **密封递交与盲收原则**：在征集文件设定的截止时间（Deadline）到达前，所有供应商递交的报价文件或投标文件处于绝对加密密封状态。经办采购员执行“盲收登记”，仅记录送达时间、主体及文件哈希/封条凭据（`sealed_hash`），系统单据状态为 `SEALED`。严禁在截标前拆封、查看或向业务接口暴露价格与商务细节，杜绝泄标、串标及暗箱压价风险。
2. **截标封存与集中开标解密**：到达截止时刻，系统自动关闭递交窗口，单据转为 `CLOSED`。截标后由开标见证人/监标人核对密封凭据完整性，触发“集中开标解密事务”，原子解析并写入明细报价与总金额，状态转为 `UNSEALED / RECORDED`，同时生成不可篡改的《开标记录表》（Opening Register 快照），随后方可进入比价与专家评审。
3. **潜在供应商与准入时效控制**：
   - 目录内日常协议采购必须为已准入启用的合格供应商（`APPROVED` & `ACTIVE`）；
   - RFQ、RFP 与公开招标寻源允许完成基础主体信息建档的潜在供应商（`PROSPECT`）被邀请或参与竞价，以扩大竞争范围；
   - 实行“定标后/签单前正式准入（Post-qualification）”：综合评审入围并拟定标授予的潜在供应商，必须在**采购订单正式核准生效（含合同派生订单签前核准）前**通过正式准入审批；未准入供应商禁止生效合同或下达正式订单。

### 5.4 变更控制

变更单针对一个合同或订单的确定版本。草稿编辑可直接修改；已生效文件改变范围、价格、日期或付款条件必须提交变更审批，需要双方确认的条款还应保留确认凭证。

批准变更时锁定当前承诺版本和相关预算：增加部分补占预算，减少部分仅释放未履约占用，已经收货、验收、开票或实付的部分不得通过改小原单据抹除。对已发生业务的纠错、退货、贷项或退款使用独立凭证。

框架协议新版本只供后续新订单引用，已有订单保留原协议版本；固定范围合同涉及已有订单的变更按统一订单执行规则的关联变更包统一审批和应用。两个针对同一基准版本的变更不能都直接生效，后批准者须重新评估差异。

### 5.5 状态及关键动作

主流程的全部角色动作见[逐步执行流程](../README.md#逐步执行流程)。以下状态是服务端实施依据，不直接照搬 IBM 界面的 Issue、Complete 等按钮名称。

| 对象 | 主状态 | 关键约束 |
| ---- | ------ | -------- |
| 申请、方式例外、授予 | 草稿 → 审批中 → 已批准；另有退回、拒绝、取消 | 申请批准冻结版本并建立预算预占；取消或终止释放预占；来源已被使用时不能直接取消 |
| 采购任务 | 待分配 → 已分配 → 处理中 → 已完成；另有取消 | 改派留历史；完成只代表委派工作结束 |
| 供应商准入 | 潜在(PROSPECT)/草稿 → 审批中 → 已准入(APPROVED)；另有退回、拒绝、取消 | 潜在供应商可参与寻源；合同/订单核准前必须正式准入且启用，完成准入后重新评估核准路径 |
| 征集文件 | 草稿 → 审批中 → 已批准 → 征集中(OPEN) → 已截止(CLOSED) → 已开标(UNSEALED) → 已授予；另有退回、拒绝、取消 | 截标前密封递交；截标后集中解密并记录开标事实；发布版本冻结 |
| 响应 | 已递交密封(SEALED) → 已开标(RECORDED) → 有效或无效；另有已撤回、已替代 | 截标前加密封存；开标事务解密生成开标记录；版本不可覆盖 |
| 合同 | 草稿 → 审批中 → 已批准 → 待生效 → 生效 → 关闭；另有退回、拒绝、终止 | 签署事实单独记录；固定范围合同审批通过时，通过派生订单明细签前锁定正式承诺占用；审批时必须校验供应商 APPROVED/ACTIVE；已批准版本生成受控待签文件；签署登记后激活生效，不因预算不足拒绝生效 |
| 订单 | 草稿 → 审批中 → 已批准 → 已下达 → 关闭；另有退回、拒绝、取消 | 审批时必须校验供应商 APPROVED/ACTIVE；获批 RFQ/RFP 无合同、无偏离、公司允许且准入/预算/范围有效时自动核准并结转对应预占；潜在供应商或有偏离订单经准入及审批后结转；下达保留送达依据；交付与结算另设派生状态 |
| 变更单 | 草稿 → 审批中 → 已批准 → 已生效；另有退回、拒绝、取消 | 已批准但待双方确认时不改原义务；应用变更只执行一次 |
| 非实物验收 | 草稿 → 审批中 → 已确认；另有退回、拒绝、已冲销 | 明确命中免审批规则时可直接确认；审批与提交职责分离；确认后修改走纠错 |
| 收货、退货、领用、库存调整 | `DRAFT → POSTED`，或先经 `IN_REVIEW → APPROVED`                                      | 收货和领用按授权直接过账；退货、期初和盘点调整先审批；过账后仅通过冲销修正            |
| 发票 | 草稿 → 复核中 → 已确认；另有退回、拒绝、作废 | 应付只计有效已确认票据；待复核分配也预留履约可开票额 |
| 付款申请 | 草稿 → 审批中 → 已批准 → 已结清；另有退回、拒绝、取消 | 提交时预留可申请额；批准生成授权，已实付部分不可撤销 |
| 付款授权 | 有效 → 已用尽；另有剩余额已撤销 | 已用金额从付款登记派生；授权本身不能标记已实付 |
| 付款登记 | 待复核 → 待补正/待核实 → 已确认；已确认纠错后可为已更正 | 出款事实及占用不因退回而消失；没有直接拒绝或撤销实付的动作 |
| 预付核销 | 草稿 → 复核中 → 已确认；另有退回、拒绝、已撤销 | 核销不再次支付；待复核即冻结预付余额及发票可结算额 |

审批主体和权限不能因页面由助手打开而改变。助手可解释、比对、准备草稿及按委托提交；审批、签署、正式验收、库存过账、支付授权和财务复核均由授权人员完成。

订单另有按明细派生的 `delivery_status`（未收/部分收/收齐/已终止）和 `settlement_status`（未开票/部分开票/已开票/部分付款/已付款/异常）。不能用一个主状态同时表达交付和付款。订单 CLOSED 表示交付义务已完成或取消，不禁止已有应付继续处理。

首期订单发布表示“生成正式单据并由采购员登记已送达”，不声称自动通知供应商。报价不足最低家数时，需要带原因的采购方式例外审批；不允许智能体自行补造报价。

### 5.6 审批与修订

1. 提交时验证字段、金额、来源单据与规则，生成不可变内容快照、规则版本、具体审批人和顺序节点。
2. 每个决定校验当前用户、节点、单据内容版本和锁版本；并发重复点击只能生效一次。只记录最终成功事务的正式审批决定。
3. 初次申请及普通单据退回/撤回后按版本修订；已批准申请专走 5.6.1，不释放原有效预占。审批中禁止直接编辑关键字段。
4. 审批人停用或离职时由获授权人员显式改派，保存原因与轨迹；不静默跳过节点。
5. 订单最后审批在一个事务内完成预算占用、来源数量占用和状态更新。余额不足时整个决定回滚，保持待审批并提示补预算后重试。
6. 发布订单前重新检查供应商有效状态、审批版本与预算占用是否仍有效。获批后的价格、范围和日期调整通过引用基准版本的变更单办理，生效时同步校验剩余义务及预算差额。

### 5.6.1 已批准申请的修订与终止

申请主表 `approved_revision` 指向有效批准版本，通用 `revision` 指向当前工作内容；不能用工作版本覆盖有效采购依据。初次草稿修改与已批准申请变更分开，后者使用 `request_change_request`，记录原批准版本、提案版本、受影响的稳定需求项和理由。

申请人提交关键范围、数量、金额、币种、类别、预算承担或交期修订时，先创建可审阅的新版本；受影响需求项立即标记 REVISING，禁止新征集发布、授予或订单核准消费该范围，现有订单照常履约及结算。未改变采购依据的说明补充仅记澄清，不重开审批。

提案审批中保留旧版本的剩余预占，不先释放。批准时锁申请、全部受影响需求项、源分配与按 ID 排序的预算账户，重新计算跨版本已占范围；新总需求不能小于已下单有效范围。仅对未下单范围重新确定预算分配：同事务释放旧余额、建立新余额，新增金额检查最新可用额，换账户或币种同时锁两端并保留各自汇率；不足则整个批准回滚，旧批准版本与预占不变。历史订单始终引用历史申请行和预算分配，不能迁移引用到新版本。

标的身份、计量单位或金额范围币种变化时，不复用原稳定需求项；关闭其未下单余量并新建需求项。已有订单范围、价格、验收或支付条款的改变须使用订单/合同变更包，不能只重审申请。提案获批后使受影响的旧征集/授予及订单草稿过期，通知采购员重新整理并审批，不静默套用新版本。

提案退回保持该范围冻结，待修改重提；拒绝或主动撤回则关闭提案，恢复原批准版本的 ACTIVE 范围，旧预占不动，清空 active_change_id，原工作草稿保留历史。只终止部分未下单范围时，采购员或申请人提交 TERMINATE 变更单，原申请审批角色独立批准，原子释放该范围预占并减少可采购范围；全部未执行范围终止后才可关闭申请。寻源轮次失败或撤销只结束该轮征集，不自动释放需求预占；放弃采购必须显式申请终止。

### 5.6.2 方式审批、订单核准及开标权限

订单草稿核准路径初始为 UNASSESSED。需要人工审批时，提交动作同事务创建审批实例并进入 PENDING_APPROVAL；待准入为 PENDING_QUALIFICATION，不使用待审批状态表示未提交草稿。

采购方式决定是独立单据，按公司、类别、金额及例外标志匹配版本化规则。采购员提交，采购方式审批人处理所有需审批的决定（正常方式及例外）；明确命中免审批规则才可记录批准。未批准决定不得发布征集或据此下单，例外审批不能替代订单批准。

订单核准按如下顺序路由，每个结果都有待办：

1. 来源版本过期、需求冻结、方式未批准：阻止提交并通知采购员修正；不自动换来源。
2. 获选供应商未完成正式准入：状态为 PENDING_QUALIFICATION，分配准入待办；完成后采购员执行“重新评估核准路径”，重查全部条件，不自动沿用过期审批。
3. 获批 RFQ/RFP、无需合同、所有关键字段一致、公司规则明确允许自动核准、准入及预算/范围有效：同事务 AUTO_APPROVED。关键字段包含公司、供应商、范围、数量/金额、币种、税率、单价、交期、交付方式、付款条件和预算分配。
4. 协议下单、例外采购、任何实质偏离或公司要求人工审批：采购员提交时创建审批实例并进入 PENDING_APPROVAL，订单审批人审核。预算不足保留可重试待办，不视为自动获批。
5. 固定范围合同派生订单：随合同审批且无偏离时 CONTRACT_APPROVED，签前预算锁定、WAITING_CONTRACT；有偏离则返回合同/订单修订，不走无合同自动核准。

执行路径、政策版本、来源指纹及审批实例持久化到订单。前端和助手使用同一服务，不根据 RFQ/RFP 名字在页面自行决定免审。规则变化须按新提交规则重新评估，已批准实例不静默更换审批依据。

集中开标使用 `procurement.sourcing.open_bids` 权限；唯一发起角色为监标人/开标见证人，平台负责实际解密。按实际用户检查该人不是本轮采购员或盲收登记经办人，不能靠兼任角色自我见证。开标时再次验证截止、密封及最低家数/例外依据。当前采用人工独立见证触发，不设置可绕过见证的自动开标后门；若无合格人员保持待办。

## 6. 预算控制与事务示例

### 6.1 多公司、多币种与范围控制

1. 公司限定权限、供应商准入、审批规则、预算与结算范围；禁止引用其他公司的发票、预算和协议额度。
2. 交易币种、预算币种和公司本位币分别表达；汇率记录方向、来源、日期和精度。比价汇率与承诺入账汇率分开，后续更新汇率不得改写历史承诺。
3. 金额按币种的小数位规则舍入，不能固定所有币种两位。不同币种先转换再合计；原币、换算金额及舍入差额都可追溯。
4. 同一承诺明细支持按预算项拆分金额；分配合计必须等于该明细的预算口径金额。
5. 默认管理口径为申请审批通过建立预占、订单批准（含定标或合同审批派生核准）转为正式承诺占用（多退少补释放估算差额）、收货或非实物验收转执行、关闭未履约义务或取消申请释放；各公司采用不同执行时点时须绑定规则版本。发票与付款不重复消耗已执行的采购预算。
6. 发票和付款引用有效的承诺及履约依据；汇兑差额作为独立财务差异，不能反向重写采购单价。当前普通付款路径先限制支付币种与应付币种一致，跨币种结算需补充差额分录及清算规则后启用。

### 6.2 预算口径

本节为平台管理口径，不替代会计确认政策。采购承诺明细按预算项分配，分别记录交易币种与预算币种快照。以下以同币种普通订单、履约转执行口径说明；所有正式占用以订单明细为来源，合同派生订单在合同核准时签前占用，详见[合同与预算规则](#52-合同约束与统一订单执行)。

```text
可用预算 = 当前批准额度 − 预占金额 − 承诺占用 − 已执行金额
```

| 事件                         | 预占金额               | 承诺占用               | 已执行             | 可用预算             |
| ---------------------------- | ---------------------- | ---------------------- | ------------------ | -------------------- |
| 申请审批通过                 | 增加申请估算金额       | 不变                   | 不变               | 等额减少             |
| 申请取消或寻源终止           | 减少对应预占金额       | 不变                   | 不变               | 等额恢复             |
| 订单批准/合同核准签前锁定    | 仅结转本次范围对应的预占       | 增加订单明细含税金额  | 不变               | 差额调整（多退少补） |
| 分批收货/非实物验收          | 不变                   | 按该批订单计价金额减少 | 等额增加           | 不变                 |
| 取消未履约部分               | 不变                   | 减少对应剩余承诺占用   | 不变               | 等额增加             |
| 合法退货（不补货）           | 不变                   | 不恢复占用             | 减少原收货计价金额 | 等额增加             |
| 发票确认、付款登记           | 不变                   | 不变                   | 不变               | 不变，避免重复扣预算 |

示例：预算 100,000 元，采购申请估算 22,000 元获批后，可用 78,000、预占 22,000；核准 20,000 元订单（含合同派生订单）后，预占结转为承诺占用 20,000、释放 2,000 估算差额，可用调整为 80,000；收货 12,000 后，承诺占用 8,000、已执行 12,000、可用仍为 80,000；关闭剩余 8,000 后，可用恢复为 88,000。

含税口径由后端统一计算。首期额外运费等应在定标前形成明确的行价格，不自动分摊未知费用。发票超出订单金额不能直接计入新预算支出，应先处理采购依据和预算授权。

预算调整必须审批且有流水，降低额度后不得小于预占、承诺占用与已执行之和。预算期间关闭后禁止新订单占用和额度变更；已有占用可继续履约，并保留其原预算期间。跨期退货冲减原占用所属账户，报表同时展示发生日期与预算归属期间。

### 6.2.1 逐行预占、部分下单与并发结转

`request_budget_allocation` 冻结每个批准申请行的预算承担和估算汇率，`budget_preencumbrance` 持有未采购范围及预算币余额。`order_source_allocation` 指明本次消费哪个稳定需求项及批准行；`order_budget_allocation` 指明消费各预算分配的份额、订单原币金额、正式汇率和预算币金额。`budget_reservation` 按订单预算分配建立，一行订单可关联多个预算账户。

每次核准只按本订单消费的范围比例结转。设该来源预算分配剩余范围 R、剩余预占 P，本次消费范围 q，则本次原预占份额 p = 按预算币精度舍入(P × q / R)；q=R 时取全部剩余 P，吸收尾差。每个预算分配按相同范围比例消费；正式承诺 c 使用本次成交金额及批准的承诺汇率，不能直接沿用估算金额。

同事务执行剩余范围减 q、预占减 p、承诺加 c；差额 c−p 消耗或恢复可用额，其余范围的预占一分不释放。TRANSFER 流水同时记录 preencumbered_delta=-p、reserved_delta=c、scope_delta=-q，即使 p=0 也用范围变化防重复。锁定所有来源和账户后先计算整笔净变化，账户余额不足全部回滚。一个申请多个来源/币种订单并发竞争同一稳定需求项锁，禁止超范围；多个预算账户按固定 ID 顺序锁避免死锁。

例：申请 10 件、预占 1,000，首单 4 件实际 360。只释放对应预占 400 并建立承诺 360；剩余 6 件仍预占 600，可用额仅恢复 40。第二单 6 件实际 660，再结转预占 600 并额外占用 60；不能因第一单价格较低就释放整笔 1,000。若批准终止剩余 6 件，只释放 600，首单 360 的承诺与履约不受影响。

申请修订仅替换剩余预占：以上首单后将总需求改为 8 件，剩余 4 件新估算 480，批准时旧预占 600 转为新预占 480，可用额恢复 120，首单 360 保留原来源。若提案需要 800 而只有 100 可用额，新增需求 200 无法满足，则原子回滚，旧预占 600 不变。降低总需求至 3 件小于已下单 4 件时禁止批准，必须先合法处理原订单。

订单余量关闭或不补货退货恢复可采购范围时，并不自动恢复原预占。再次下单前由申请人提交未使用范围的预算重审，建立有效预占后才继续；不能仅因为数量可采购就使用已释放预算。服务按金额范围同样控制，范围单位来自批准申请而非成交金额，降价不等于可追加服务。

### 6.2.2 账户与明细对账

账户预占等于 PRE_RESERVE/PRE_RELEASE/TRANSFER 等流水的 preencumbered_delta 合计，并等于全部预占余额；正式占用等于 reserved_delta 合计并等于各 reservation.remaining_amount。有效申请范围与跨版本订单分配核对；每笔变更/关闭/退货的恢复范围只记一次。额度调整必须覆盖预占、正式占用与已执行总和；汇率快照只追加，更新汇率不能重算历史余额。

### 6.3 集中开标解密事务（Bid Opening & Decryption Transaction）

```text
开始事务
  认领幂等键，校验调用者具有开标见证权限，且实际用户不是本轮采购员或盲收经办人
  锁定征集主表（RFQ/Tender）及所属所有已登记密封响应（QUOTATION）
  校验系统时间已过截止时间（current_timestamp >= rfq.deadline）且当前状态为 CLOSED
  校验有效密封递交家数满足最低限制（或已绑定有效例外审批 exception_document_id）
  核验各家密封封条或数字凭证快照（sealed_hash）完整未被篡改
  解密各家响应内容，原子写入 quotation_line 标的明细与含税合计 gross_amount
  生成不可篡改的《开标记录表》（Opening Register 快照，记录开标价格、递交时间与监标人员）
  将 RFQ 状态置为 UNSEALED，各有效报价状态置为 RECORDED，记录解密时间 unsealed_at
  写业务审计、开标解密日志、幂等成功结果
提交事务
```

### 6.4 统一订单核准及合同签前锁定

核准入口包括普通订单审批、满足规则的定标派生核准、固定范围合同审批。三种入口调用同一个订单核准领域服务；审批依据分别记录，不能用合同头充当预算来源。

固定范围合同送审时已包含派生订单草稿、明细、预算分配和支付计划，审批人可审阅完整范围。最终核准事务如下：

```text
开始事务
  认领幂等键；校验当前用户、审批依据和冻结内容版本
  按 11.1 统一顺序锁合同/订单/申请根文档、稳定需求项、来源明细、分配及预算账户
  校验公司、供应商准入、币种、来源范围、协议剩余额与批准版本一致
  按订单明细将申请预算预占转为正式占用，差额多退少补
  占用合同可下单范围；写订单 APPROVED 与实际审批依据
  合同审批入口同时写合同 APPROVED、受控待签版本及订单 WAITING_CONTRACT 执行资格
  写审计、变化事件及幂等结果
提交事务
```

同一合同审批版本与派生范围通过唯一生成键去重；失败全部回滚，不出现合同已批准却没有派生订单或没有预算锁定。框架本身无确定采购义务时不生成空订单，后续每次下单才核准并占额。

### 6.5 合同生效、订单下达与终止

合同生效事务锁定合同和待执行派生订单，核验签署凭证、版本及生效条件，登记 ACTIVE 并将订单执行资格改为 READY；不再次占预算。合同未生效时，订单即使 APPROVED 也禁止下达、收货、验收和付款申请。之后采购员登记订单送达，可引用合同签署文件作为送达依据，将订单置为 ISSUED；下游写入统一检查订单已下达和执行资格。

终止未签合同使用同一锁顺序，校验真实签署状态及派生订单未执行，批准后同时终止相关订单并释放剩余占用；与合同激活互斥。已签或已有履约、发票、预付的合同终止先处理各订单剩余义务及财务差异，不能仅关闭合同头释放全部预算。

涉及固定范围合同及已有订单的联动变更，用一个变更包冻结每张订单的基准版本和差额；审批及必要的双方确认完成后，按同一锁顺序原子更新合同/订单有效版本、协议额度和订单预算差额。任一来源过期或额度不足全部回滚，不能合同已改而订单仍执行旧的冲突义务。

预算余额不能通过“先在事务外查询，再更新”实现。所有竞争同一预算账户的操作需取得账户行锁，库存和付款也遵循对应聚合锁规则。PostgreSQL 行锁用于串行化竞争更新，但应用仍要明确锁顺序和业务校验。[PostgreSQL 显式锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)

## 7. 库存与履约验收

### 7.1 到货、检验、退货与非实物验收控制

**实物采用到货记录、检验结果、合格收货三层对象。** 到货事实不等于质量合格或可用库存。首期以独立到货保管台账跟踪待检和不合格品，不计入采购库存余额；记录公司、保管位置、来源订单明细、数量和交接人，不能从保管台账领用。需要专业检验的物料由质检员出具结果；规则允许简化验收的物料由仓管员核验后放行，不强制所有物料都建立多日 IQC 流程。

每个到货明细按数量拆分处理，不用一个整单状态覆盖部分合格：实到量 = 当场拒收量 + 后续未入库退回量 + 已过账入库量 + 仍保管量。仍保管量细分为待检、合格待入库和不合格待处理；各项非负且互斥。已入库后的正常退货另记，不倒减原到货的已入库历史数量。检验结论可分批形成；复检追加新版本并重新分配未入库数量，不能覆盖已经入库使用的结论。

仓管员登记当场拒收或未入库退回的实际交接，采购员负责供应商沟通。拒收与未入库退回不增加或冲减采购库存，不触发预算执行或释放采购承诺；原交付义务仍待履行，不再采购则另办余量关闭。合格收货过账必须锁定来源明细、到货合格余额和相关库存预算，在一次事务内验证可入库数量并更新库存、履约和预算。待检期间可以显示“已到货待验”，不能显示已验收或用作可开票依据。

**已入库退货按动作授权，不限定只能由采购员发起。** 退货申请人可以是获授权的仓管员、质检员、使用人或采购员；记录实际发现人、原收货明细、问题数量和证据。采购员确认供应商接收、索赔及退款/补货安排；涉及发票或付款时由财务核实处理路径；独立退货审批人批准后，仓管员登记实际退货并过账。使用人发起不代表获得库存写权限；已领用货物须先办理真实回库，不能直接扣仓库库存。

**非实物验收提交和正式确认分开。** 提交时冻结范围、金额、期间、成果证据和规则版本。审批规则按公司、类别、风险等级、合同/订单承诺总额及本次/累计验收金额匹配；阈值由公司配置，不因拆分验收单而绕过大额审批。大额或高风险验收必须有独立于提交人的最终审批人，可按规则设置业务负责人、项目负责人等顺序节点；首期不以支持任意会签为前提。只有明确命中低风险免审批规则才允许直接确认，记录规则判断与操作者；缺少配置或合格审批人时保持待处理。

审批中、退回及拒绝的验收不转预算执行，也不增加可开票额度。最终批准与验收确认、履约汇总及预算更新同事务生效；并发验收锁定来源明细并校验累计数量、金额和服务期间，防止超额或重复确认。退回后修订重新审批，已确认结果只能通过纠错处理。验收审批不是发票复核或付款授权，后续财务步骤仍独立执行。

### 7.2 收货和可用库存

订单行累计收货量指已过账数量，减去纠错冲销；正常业务退货另外记录，不把退货直接覆盖为“从未收货”。首期正常退货不要求补货，替换采购重新申请或使用释放的申请余量。

```text
待收数量 = 订购数量 − 已取消数量 − 累计收货数量
净收货数量 = 累计收货数量 − 正常退货数量
库存余额 = 期初 + 入库 − 出库 ± 调整
```

首期到货待检和不合格品采用独立保管台账，不计入采购库存余额且不可领用；采购库存只在合格收货过账后增加。首期不实现库存预留，可用库存等于该合格库存余额，并在页面注明“不含未来领用承诺”。采购建议可以展示待收订单数量，但不能把它计为现有库存。

收货过账先验证公司、检验规则版本及合格结论，锁定采购来源明细、到货合格待入库余额、预算账户和库存余额，在同一事务内校验待收量、更新收货与库存流水、把预算占用转已执行并记录变化。超量收货默认拒绝；短收可分批继续。订单待收量全部为零时关闭交付义务。

### 7.3 退货与纠错

当场拒收及未入库退回使用到货交接记录，不建立库存退货流水或预算执行冲回。已入库退货由获授权的退货申请人发起，现场发现者或采购员均可担任；采购员确认商务安排，财务按关联情况核实，最终审批人与申请人分离。以下规则仅适用于已入库退货。

- 退货关联原收货行，检查可退量、当前仓库库存和发票分配；审批通过后才可过账。退货减少库存和预算已执行，增加申请可采购余量，不重新打开原订单待收量。
- 退货与发票确认互斥地锁定同一收货行。首期存在有效发票分配或待复核分配的数量不能直接退货，返回明确异常待办。
- 对未付款且无待复核付款的发票，可先通过财务作废释放分配，再退货并登记正确发票。已付款或需要红字/贷项处理的退货在首期属于人工例外：保留关联工单和原始记录，在财务调整能力补齐前不伪造平台账务闭环。
- 错误收货的冲销与正常退货分开：若冲销数量没有下游发票、未正常退货且库存足够，审批冲销会反向记库存流水、已执行转回占用并重新打开待收量。有关预算期间和订单已取消余量需重新校验。
- 已发生领用导致库存不足时不能冲销或退货；先登记真实的库存回库或调整依据。盘点不得被用来绕过退货和财务关联限制。
- 期初、盘点和库存纠错单审批后过账。盘点保存观察时库存版本，执行时版本改变则要求复盘或人工确认新差额，防止覆盖盘点期间的出入库。

库存余额是事务维护的查询汇总，库存流水是追溯依据。每日核对汇总与流水，差异创建异常，不自动静默重写余额。

## 8. 发票、预付与付款控制

### 8.1 支付计划与预付分支

普通付款基于已确认应付；预付款基于可执行订单中已批准的支付计划，不要求先收货或先建立虚假的验收记录。框架协议额度本身不是可付款依据。计划逐项记录承诺明细、类型（预付/验收后付款）、金额或比例、币种、触发条件、到期日及版本，计划金额合计不得超过同范围有效承诺金额；预付上限、审批角色和所需凭证由公司制度配置。

预付计划获批不代表触发条件已满足。付款申请人提供签署、生效、供应商付款请求等条件证据，付款审批人核准后才授权支付。即使先收到票据，也只登记原件及采购依据，标记待履约匹配，不通过伪造收货确认普通应付。预付授权与普通应付授权分开标识，不能针对同一范围既走预付又全额走普通付款。

允许分次预付，只有经独立复核确认的实际已付部分进入可核销余额；单纯获批或待核实的款不能核销。履约和发票确认后，财务登记人提交预付核销，财务复核人确认，将对应预付余额用于结清发票。核销本身不产生新的现金支付，不重复消耗采购预算。预付时预算仍处于承诺占用，按本平台履约转执行口径，在真实合格收货或验收确认时转执行。

外部产品也区分预付款与后续发票核销，并在核销时减少可用预付余额，参见 [Oracle 预付款说明](https://docs.oracle.com/en/cloud/saas/financials/26a/fappp/prepayments.html)。这里采用的是本平台支付计划与已付分次余额模型，不照搬其预付款发票对象或完整会计处理。

### 8.2 额度公式与防重复支付

- 预付计划可新申请额 = 获批预付额度 − 该计划累计已确认预付实付 − 未结清预付申请占用。后续核销不恢复预付计划可支付额度。
- 预付可核销额 = 已确认预付实付 − 已确认核销 − 待复核核销占用 − 已退款或退款处理中冻结金额。
- 发票可新申请付款额 = 已确认应付 − 直接分配给该发票的已确认实付 − 已确认预付核销 − 待复核核销占用 − 未结清普通付款申请占用。
- 授权可新执行额 = 授权有效总额 − 已确认实付 − 执行中/待复核/待补正/待核实的执行冻结额。每笔执行在这些状态间转移，同一金额不重复扣减。

申请占用包含审批中金额以及获批授权尚未转为确认实付的余额；其内部的执行冻结额不在来源发票或计划上再扣一次。拒绝、退回或撤回的是尚未执行的付款申请，才能释放对应占用；已出款记录退回不释放它。

同公司、供应商、币种且属于相同承诺范围才允许核销。普通付款授权前必须处理该范围的未结清预付计划：未执行的预付申请/授权经批准关闭，已付预款先核销或冻结待处理，执行中或待核实预付则暂停该范围新增普通支付。不能因预付暂未核销而把全部发票金额再次授权出去。

示例：采购承诺 100，预付计划 30、验收后付款计划 70。确认实付预款 30 后，可核销余额 30，预付计划可新申请额为 0；履约并确认发票 100 后，核销 30，再申请尾款 70。核销后预付可用余额为 0，但预付计划可新申请额仍为 0，总现金支出为 100。

提交核销时同时锁定预付余额和发票可结算额，建立双边占用；确认时同事务转为有效核销，退回或拒绝释放核销占用而不删除预付实付。撤销已确认核销须独立复核，原子恢复两端余额并重新冻结受影响的普通支付，不产生新付款。存在核销或支付占用的发票不能直接作废。

### 8.3 线下支付事实与登记复核

付款经办人在线下出款前认领支付执行任务，平台锁定授权可执行额。执行记录与付款登记分开：前者防止重复发起同一笔支付，后者核实真实支付及其分配。出款结果未知、超额、无授权或暂无法关联发票时，仍保存实际流水和凭证，进入待核实台账，不能因匹配校验失败拒绝保存事实。异常金额及可识别的授权范围冻结，暂停相关再支付，交财务处理。

登记复核仅允许确认、退回补正或转待核实，不允许直接拒绝、删除或将真实款项标为未支付。退回时保留支付事实、原始凭证、授权执行冻结和来源占用；重新提交沿用同一执行记录，不能再次占款或重新生成支付任务。只改凭证说明不改变金额；金额、收款方或来源关联的修订保留版本并独立复核，在核实前不释放原冻结。确认后冻结转为实付，退回不意味着银行退款。

未执行或经凭证证明失败的执行任务，由独立复核人确认后才可释放冻结；结果未知不能按失败处理。重复录入需关联已存在的同一真实流水，独立确认后合并分配和占用，不能恢复重复可付额。已确认错录通过更正记录转移正确的来源分配，保留支付事实；无法确定正确去向时转待核实，不直接冲销为零。

银行退款是新的资金流入，必须有独立退款凭证及复核，不能通过冲销登记模拟。预款取消采购时冻结未核销余额并建立退款待办；未退款或未完成合规结算前不得收尾，也不自动重新开放原预付计划。完整贷项及退款结算仍按后续切片实施，未支持时保持显式待处理余额。

报表分别展示已确认实付、待复核/待补正/待核实款和预付未核销余额；人工导入银行流水或核对水单逐笔匹配执行记录。存在未解释资金差异的采购不能关闭，不能仅以已确认付款统计声称全部对账完成。

### 8.4 发票匹配与事务边界

普通应付确认须核对公司、供应商、币种、有效履约数量或验收金额、单价、税率、税额和总额。数量扣除已有有效及待复核分配；按金额验收的服务使用获批里程碑或期间金额，不虚构单价。单价默认与获批采购依据一致，调低或调高均须解释；价格变化不能仅因小于订单价就自动放行。税率按获批依据及已配置税务口径校验，差异记录后由财务核实，必要时先办理采购依据变更。

行未税额、税额及总额按币种和税额舍入规则计算并核对票面，记录原值、计算值、差异、容差规则版本；合法容差须经批准配置，不能把舍入容差用于豁免数量、未经批准的价格或税率变更。[Oracle 发票容差说明](https://docs.oracle.com/en/cloud/saas/financials/26b/faipp/invoice-tolerances.html)也将匹配差异及容差作为单独控制；本平台沿用更明确的获批价格一致性规则。

付款申请、执行认领、实付复核和预付核销分别具有幂等键、版本与范围权限。跨来源先按 11.1 统一锁集合顺序取得根文档和来源锁，再处理预付、申请授权及执行余额，校验与流水/余额/状态/审计同事务提交；核销与普通支付并发时不能各自使用同一份余额。

### 8.5 发票分配、复核与纠错

首期每张发票属于一个供应商，可关联多张同法人、同币种订单。每个发票行明确关联一个订单行，再分配到一个或多个合格收货行或已确认非实物验收行；无法关联时保持草稿，不按供应商名称或金额相近自动入账。

匹配分两步：`match` 生成可重复运行的分析快照，不占用收货量；`submit` 在事务内重新匹配，建立待复核分配并冻结内容，防止多个发票同时占用同一批收货。财务复核时再次校验版本和匹配结果，将待复核分配转为有效分配。

匹配规则见上一节。默认舍入容差为 0；规范化发票标识唯一，作废后也保留，录入纠错使用同一业务对象的新版本。匹配快照保存订单、履约、退货和规则版本，提交及确认时重新验证。

匹配状态为 `NOT_RUN/PASSED/FAILED/STALE`，与发票审批状态分开。匹配快照不得直接作为付款依据。发票退回、拒绝或撤回时释放待复核分配；重新提交重新校验。发票 CONFIRMED 后形成平台应付金额。

录入纠错与真实发票作废分开处理。确认记录通过纠错审批作废并释放分配后，若只是平台录入错误，可显式 `revise` 在同一发票 ID 下建立新的 DRAFT 内容版本，保留原 VOIDED 版本、所有明细和审批；若原票据已真实作废，则不能修订为有效票据，替代发票按新标识登记。分配必须绑定具体发票内容版本和明细 ID。

普通应付付款前必须匹配通过并完成财务复核；预付款按生效采购承诺的获批支付计划及触发条件授权，无需伪造履约匹配。舍入容差即使允许确认，也单列差额供财务检查；订单预算仍按订单与收货口径统计，不悄悄改写订单单价。

### 8.6 结算验收场景

- 承诺 100、预付 30、尾款 70：未验收时只能按获批条件预付 30；确认履约及发票 100 后核销 30，尾款只能申请 70，核销不再记现金或预算支出。
- 同一预付同时核销两张发票，或核销与普通支付并发：两侧有效加待复核占用均不超余额；已核销预付款不得再次支付。
- 单价高于或低于获批单价、税率不同、税额及总额不符：均有明确差异；舍入容差不得掩盖未批准的商务变更。待检、拒收和重复开票数量不得进入可匹配额度。
- 实付 30 退回补证或转待核实：原执行冻结仍为 30，无法再次执行这 30；补正确认只结转一次。无授权流水、结果未知及重复录入均保留追溯记录。
- 先票后履约可保存真实票据，普通应付保持待履约匹配；付款走独立预付计划。取消预付采购时未核销余额冻结并进入退款待办，不自动释放为新支付机会。

## 9. 权限、身份与数据保护

### 9.1 授权模型

最终权限 = 身份有效性 ∩ 动作权限 ∩ 数据范围 ∩ 单据状态允许动作 ∩ 职责分离约束。权限在业务服务执行前验证；审批角色本身不构成对全部单据的批准权。

权限编码采用业务动作，例如 `procurement.request.create`、`procurement.order.issue`、`finance.payment.confirm`、`inventory.receipt.post`。数据范围包含法人、部门、仓库和本人；列表、详情、统计、导出、附件下载均应用相同范围。查询条件由服务端构造，不能接受客户端传入 SQL 条件。

财务敏感字段、供应商联系人和附件按字段权限返回。系统管理员可管理规则和账号，但默认不能代替业务审批；授权变更必须审计，已注销会话或已撤销委托立即失效。

### 9.2 首期登录与助手委托

统一前端部署在同一站点，平台提供账号登录和服务端会话。会话使用 HttpOnly、Secure Cookie；有状态写请求校验 CSRF，明确允许的来源。密码散列、随机令牌生成和签名使用成熟组件，实施时锁定依赖；登录节流、退出、用户停用和会话撤销属于基础能力。

助手不直接读取平台会话数据库。用户在前端授权助手动作时，由平台签发短期、可撤销的委托凭证，绑定用户、服务客户端、组织、动作范围及目标业务对象（如适用）；助手还需证明自身服务身份。平台每次校验凭证和用户当前权限，实际授权取用户权限、委托范围与助手工具白名单的交集。

委托凭证仅表示“允许代表用户执行某类动作”，不代表单据已通过审批。首期助手不获准准入审批、预算调整、库存过账、财务复核和付款登记。定时任务仅使用限定组织和只读范围的服务身份。

### 9.3 附件与审计

附件保存到受控存储，数据库记录对象键、大小、类型、摘要和所属单据；首期可使用持久化文件卷，禁止放在容器临时目录。下载通过鉴权接口，不暴露本机路径或永久公开链接。上传校验大小、内容类型和文件名，不执行附件内容。

成功的业务审计与单据写入同事务提交；被拒绝的越权请求记独立安全日志。审计保存调用服务、实际用户、时间、动作、单据版本、必要变更摘要、原因、请求 ID 和助手任务 ID。日志不保存密码、会话令牌、完整委托凭证。

## 10. API 契约与助手接入

正式下达、收货过账、验收确认及付款申请须验证订单已下达及 READY 执行资格、来源和当前动作权限；待合同生效订单不可执行。订单交付关闭不阻止已有合法发票和付款结算；预算执行后不能要求原承诺占用仍等于订单全额。供应商停止新采购禁止新核准及下达，不自动冻结历史履约与结算；专项质量或支付冻结由明确对象和理由控制。到货事实、拒收、异常实付允许真实登记，权限校验不等于把不合规事实拒之系统外。

### 10.1 统一约定

API 前缀 `/api/v1`。以下为实现契约草案，不表示接口已上线。列表支持过滤白名单、稳定排序和不透明游标，默认每页 20、最大 100；详情返回 `revision`、`lock_version` 和 `allowed_actions`。分页默认按创建时间和 ID 排序，不提供任意字段排序或无限量返回。

- `GET` 查询，`POST` 创建或执行业务动作，`PATCH` 仅修改可编辑草稿或主数据白名单字段。
- 修改已有对象携带 `expected_version`；不匹配返回 409，不覆盖其他人的修改。
- 所有业务写请求携带 `Idempotency-Key`。作用域为法人、调用主体/委托用户、业务动作和键；服务端保存规范化请求摘要，重复同内容返回原结果，同键不同内容返回 409。
- 幂等成功结果与业务写入同事务提交；并发同键依赖唯一约束串行处理。失败回滚后可重新执行；客户端超时必须保留原键，不生成新键重试。
- 成功创建返回 201，普通动作返回 200，持久化后台作业返回 202 和可查询的 `job_id`；不把仅启动一个进程内函数视为持久化成功。
- 错误使用 401（身份无效）、403（动作无权）、404（不存在或不可见）、409（版本/状态/额度冲突）、422（字段无效）、503（暂时不可用）。响应包括稳定业务错误码和请求 ID。

```json
{
  "error": {
    "code": "BUDGET_INSUFFICIENT",
    "message": "预算余额不足，订单仍处于待审批状态",
    "details": {"available": "8000.00", "required": "10000.00"},
    "request_id": "request-uuid"
  }
}
```

| 附件/报表      | `POST /attachments`、`GET /attachments/{id}/download`、`GET /reports/procurement-summary`                 | 鉴权上传下载和汇总                                           |

草稿详情、编辑和列表按模块补齐，但不生成能修改任意状态的通用接口。预算预占/占用/释放只作为内部业务服务，由申请批准/变更/终止、订单、收货验收及退货流程触发，不开放余额修改 API。审批最终节点调用明确的领域处理器；例如发票复核确认、付款复核确认、纠错执行与批准记录同事务完成，库存退货批准后则等待仓管实际过账。

### 10.3 变化订阅与可靠游标

业务事务在 `business_change` 写入 UUID 变化 ID、单据 ID、版本、类型及最小载荷，不在事务中调用助手。后台发布器只读取已提交变化，在独立短事务中锁定单行 `publication_counter`，为尚未发布的变化分配递增发布序号并写 `change_publication`；更新计数器与发布记录一起提交。多个发布器通过同一锁串行分配，按变化 ID 去重。

`GET /changes?cursor=...` 按发布序号返回变化及下一游标，避免直接用业务序列号产生“较小序号晚提交而被跳过”的漏事件问题。游标签名并绑定调用主体和筛选条件，扫描包含无权限事件时仍返回安全的扫描进度，不暴露它们的载荷。权限扩大或游标过期时要求重新做授权范围快照同步，不能假定旧游标覆盖新范围。

助手至少一次消费、按变化 ID 去重；同一单据不同版本可能晚到，因此事件只触发查询，动作前以业务 API 的最新状态为准。发布器故障仅延迟智能提醒，不影响人工业务。未来加入消息队列时复用变化记录和幂等消费规则。

`GET /operations/by-key` 仅允许查询本调用主体的原操作，返回已提交结果；查不到不代表之前请求一定失败，可能尚未提交。客户端可以同键重试，由数据库唯一约束和事务确认最终结果。

### 10.4 契约管理

业务后端生成 OpenAPI，提交到根目录 `contracts/`，前端和助手分别生成客户端。开发阶段接口调整同步修改调用方和契约测试，不添加旧接口别名或转发兼容层；实际生成工作在实现接口后进行，不预先编造与代码不同步的接口规范。

## 11. 并发、一致性与异常恢复

### 11.1 事务与锁约定

平台数据库为四模块共同的事务边界。每个写用例在事务开始时校验身份，按固定顺序获取它需要的记录锁，再重新验证业务约束。统一顺序：幂等记录 → 供应商等主数据（按表名、ID）→ 所有关联通用单据（按 ID，不按申请/合同/订单业务顺序）→ 稳定需求项（按 ID）→ 来源明细及分配/预占记录（按固定表序和 ID）→ 预算账户（按 ID）→ 库存余额（按键）。固定来源表序为合同明细、申请行、征集/授予行、订单行、履约行、申请预算分配、预占、订单来源分配、订单预算分配、正式占用；仅锁本动作用到的表。新增资金与保管对象在来源明细阶段按以下子序列统一加锁：到货主记录、到货行、检验记录、发票行、支付计划行、付款申请行、授权、执行、实付登记、实付分配、预付余额、核销行、未决工单；同表按 ID。多来源操作预读完整集合后加锁，不在持锁后反向追加父级锁；关联变化则回滚重试。所有用例遵守相同顺序，不按用户传入的行顺序加锁。预读用于确定锁集合，获取锁后重读并确认关联未改变；供应商停用与订单发布也必须锁定同一供应商记录。

同一个订单、发票、收货的提交与取消都锁相同的单据或来源明细；增加新行时也锁其父单据，防止只锁已有子行却遗漏并发插入。库存余额首次创建使用唯一约束与冲突处理，随后锁余额行。预算账户必须预先创建，不在扣减过程中自动补建空账户。

金额与库存依赖数据库事务、行锁及约束共同保证；乐观版本主要保护用户编辑。死锁或可重试数据库错误仅在整个事务回滚后做有限重试，仍用原幂等键，不对业务拒绝无限重试。

### 11.2 关键异常行为

| 场景                       | 预期行为                                                 |
| -------------------------- | -------------------------------------------------------- |
| 两个订单同时竞争最后预算   | 一个成功，另一个余额不足；不能都获批                     |
| 两个订单使用同一申请剩余量 | 锁来源行重新校验，拒绝超量分配                           |
| 相同收货请求重复发送       | 返回同一过账结果，只产生一次库存和预算流水               |
| 收货与取消订单余量并发     | 锁同一订单/来源行，后执行者按最新待收量重新校验          |
| 发票提交与退货并发         | 锁同一收货来源，禁止重复占用或退掉已分配数量             |
| 两笔付款同时占同一发票余额 | 待复核分配也占余额，拒绝超付登记                         |
| 审批规则调整               | 已在途实例使用提交时快照；紧急终止需要显式操作和审计     |
| 助手断线、重启或重复任务   | 业务不回滚；助手通过幂等键、单据状态继续                 |
| 写入成功但 HTTP 响应丢失   | 同键查询或重试得到原结果，不重新建单                     |
| 发布器或任务进程停止       | 待发布记录留存，重启后继续，不丢业务变化                 |
| 汇总与流水不一致           | 产生异常并限制相关高风险写入，经核实后修复，保留修复审计 |

库存、预算、发票占用和付款余额的派生汇总定期与明细核对。报表返回统计时间和口径，不以过期缓存作为写入校验依据。

| ---------- | ----------------------------------------------------------------------------------------------------- |

### 12.1 异常责任与供应商评价

异常负责人是每张异常工单指派的实际用户，不是拥有全公司关闭权限的新岗位。按公司和异常类别匹配责任规则：交付逾期归采购员、质量问题归质检员、服务验收差异归业务验收人、票款差异归财务人员。规则无法确定或责任人离岗时，由对应模块负责人改派并记录原因。工单保留负责模块、责任人、指派人、历史和证据；只有被指派且具备该类处置权限的人可以提交关闭，关联纠错或财务未决事项未完成时后端拒绝关闭。关闭工单不替代验收、财务复核或资金记账。

供应商评价由各角色提交各自维度：仓管员评价到货配合与外观交接，质检员评价质量，业务验收人评价服务/成果，财务人员评价票款配合，采购员评价商务配合。系统从已确认业务记录计算及时率、合格率等客观指标，不能由采购员覆盖。按采购类型配置适用维度及权重；不适用维度标记 N/A，有效权重重新归一，必需评价缺失时显示待完善而非记零分。平台汇总，供应商管理员复核发布；采购员不代填其他角色评分。原始评价、证据、规则版本及发布快照留存，评分修改重新复核；评价工作未完成不应阻止已完成履约和结算的订单正常关闭。

### 12.2 责任与合同执行验收

新增验收：合同审批重试仅生成一次派生订单并占一次预算；合同未生效或订单未下达不能预付/履约；合同终止与激活并发只有一个合法结果；同合同多订单不超范围；非实物订单无仓库仍可验收；下游不存在合同/订单来源切换；非指派人不能关闭异常；评价者不能改其他角色评分，缺项不按零分发布。

## 13. 部署、运维与验证

### 13.1 首期部署

开发与试点使用 Docker Compose：`web`、`platform-api`、平台后台作业进程、`assistant-api`、助手 worker、PostgreSQL 和按需 Redis。平台作业与助手任务独立运行和授权；平台核心写请求不依赖助手或 Redis 在线。

业务库与助手库使用独立账号。平台数据库迁移由单独发布步骤执行，不由每个 API worker 启动时竞争执行。Alembic 自动生成迁移后人工检查，尤其关注约束、索引和数据转换；官方说明自动生成结果需要审阅和修正。[Alembic 自动迁移文档](https://alembic.sqlalchemy.org/en/latest/autogenerate.html)

提供进程存活与数据库就绪检查、结构化日志、请求 ID、慢查询记录；监控接口错误率、事务冲突、数据库连接池、审批积压、变化发布延迟及账本核对差异。连接池总量按 API 和作业进程数共同预算。

业务库与附件均持久化并备份，上线前演练恢复；具体备份频率、恢复时间和保留期限在试点容量与企业要求确定后配置。密钥和连接口令从环境或受控密钥配置读取，不提交仓库。

### 13.2 验证方式与验收场景

关键集成测试使用真实 PostgreSQL，不能只靠 SQLite 验证锁和事务。单元测试覆盖金额舍入、数量分配与状态判断；集成测试覆盖数据库约束、真实并发和完整事务；契约测试验证前端/助手输入输出及授权；业务验收通过页面完成以下场景。

| ---- | --------------------------------------------------- | --------------------------------------------------------------------- |
| A01  | 完整人工采购                                        | 助手关闭仍完成供应商、预算、申请、订单、收货、发票、付款登记          |
| A02  | 预算 100,000，订单 20,000，分批收 12,000 后取消余量 | 预算余额与第 6 节示例完全一致，库存与流水相符                         |

首期不承诺未经压测的吞吐指标。建议以 10 万订单行和 20 个并发业务用户作为试点测试数据集，常用查询 P95 目标低于 1 秒、普通写入低于 2 秒；这是拟定验收目标，须记录硬件、数据分布与测试结果后确认，模型响应不计入平台接口耗时。

## 14. 实施顺序与业务参数

### 14.1 工程落地与验收

目标范围已包含多公司、多币种和实物、服务、许可、订阅。工程按业务切片交付，不把未实现能力通过空按钮或文本字段假装支持。

| 切片 | 应交付能力 | 必须验证的业务结果 |
| ---- | ---------- | ------------------ |
| P0 公共基础 | 公司与权限、币种及汇率、分类、预算分配、版本和审批 | 不可跨公司引用；历史汇率不随新配置变化 |
| P1 RFQ 闭环 | 申请、审批、分配、需求核实、方式、询价、报价、评审授予、订单、实物及非实物履约、发票、支付计划、预付及核销、付款申请与实付 | 两种履约均可独立闭环；付款授权与实付分开；重复提交不重复占用 |
| P2 合同与协议 | 框架及服务协议、固定范围合同派生订单、协议下单、变更与到期提醒 | 同一义务不重复占预算；并发下单不超协议额度；旧订单不被协议变更覆盖 |
| P3 RFP 与招标 | 方案响应、评审标准、澄清补遗、响应封存、授予与合同衔接 | 评审引用确定版本；修改范围重新发布；缺少有效响应不能强制授予 |
| P4 复杂结算与运营 | 按实际公司制度补保留款、贷项退款、跨币种结算，完善绩效与助手工具 | 真实差异可追溯，自动化只调用已实现且授权的业务动作 |

数据库实施需先重构采购来源与履约明细，随后同步预算、发票、付款外键和接口。所有履约及结算均使用订单行，但订单字段必须支持非实物范围及金额，不能要求服务采购虚构物料和仓库。本轮字段设计已补齐，完整贷项退款和跨币种结算仍按 P4 边界实施；完成字段设计、迁移和真实数据库验证后，才可以宣称对应切片实现。

助手接口和幂等边界从公共基础切片保留，只暴露已验收能力；每个业务切片同时完成页面、API、字段设计、迁移和真实数据库验证。

### 14.1.1 本轮规则验收清单

| 编号 | 场景 | 必须结果 |
| ---- | ---- | -------- |
| R01 | 10 件预占 1,000，首单 4 件 360 | 保留余量预占 600，正式占用 360，可用额只恢复 40 |
| R02 | 两单并发申请范围 7+4，批准范围 10 | 稳定需求项锁保证最多一笔按原额度成功；另一笔重读后超量失败 |
| R03 | 两账户按 60%/40% 分配，首单采购 40% 范围 | 各自只结转 40% 的预占；汇率或某账户超额时整笔回滚 |
| R04 | 首单后将 10 件改为 8 件，剩余估算 480 | 保留旧单来源；预占 600 变 480，释放 120；拒绝/撤回不改旧余额 |
| R05 | 修改至 3 件或新增预算不足 | 少于已下单 4 件不可批准；任何预算失败不切换 approved_revision、不释放旧预占 |
| R06 | 申请修订与订单核准并发 | 同稳定需求项互斥：修订先冻结则禁止新占用；订单先占用则修订必须重算下限 |
| R07 | 跨币种非实物订单、无定标的协议订单 | 币种 FK/精度/汇率快照有效；可无仓库及物料、可无 award_id；明确合同/方式及预算来源 |
| R08 | 未下单需求终止或未签合同终止 | 仅释放目标预占或派生订单未履约占用；部分已履约及预付保留待处理 |
| R09 | 采购员兼任监标人尝试开标 | 按实际用户职责分离阻止；独立见证人过截止且有效家数满足才可执行 |
| R10 | RFQ/RFP 公司要求人工审、准入补齐或来源过期 | 均进入指定待办或重新评估；不遗漏入口，不自动绕过公司规则 |
| R11 | 正常方式也要求审批 | 决定未批准不能发布/下单；免审批须明确规则及审计 |
| R12 | 历史供应商停用、真实拒收或异常实付 | 新采购被阻止；合法历史履约及真实事实可处理，不因通用门禁抹去事实 |

本清单是实现后所需的数据库和业务集成验证，不代表已运行数据库测试；当前阶段验证字段引用、文档链接、规则覆盖及预算示例计算。

### 14.2 实施前应核实的业务参数

- 实际法人、部门、仓库和职责分离安排；哪些人可以调整审批规则。
- 采购方式、最低报价家数、金额阈值，以及单一来源的例外审批人。
- 预算按部门/项目/科目的具体维度，是否接受含税及收货转执行口径。
- 已确认的服务采购与多币种所需验收口径、币种精度和汇率来源；预付款、已付款退货、税额差异的具体制度。
- 收货是否需要独立质检，盘点调整和领用是否需要额外审批。
- 历史供应商、物料、预算和期初库存的导入来源及确认人。

上述待确认项不阻止工程基础、主数据、权限和普通采购主流程设计；涉及不同记账口径或首期范围扩大的功能，应在实现前更新本设计及对应验收用例。
